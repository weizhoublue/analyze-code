# 设计文档：code-analyzer Claude Code 插件

- 日期：2026-06-02
- 状态：已确认（待用户审阅 spec）
- 来源需求：仓库根目录 `README.md`

## 1. 目标

制作一个分析开源项目代码的 Claude Code 插件。给定一个开源项目代码库，插件梳理出该项目面向**用户的业务功能**，并产出综合分析报告。

分析聚焦于**用户业务层面**的功能，**不分析**以下工程能力：

- CICD
- 镜像打包、发布相关能力
- 测试代码

核心原则：**文档 + 代码双源综合分析**。任何开源项目的 `docs/` 目录通常包含大量关于功能与原理（含代码级别）的文档；分析必须同时充分结合文档信息与代码信息，交叉印证、调和差异，给出综合结论，而非单方面、片面分析。

## 2. 整体架构

仓库根目录本身即插件。采用「主对话 Skill 编排 + 多只读 subagent 分工」模式，以降低单 agent 的上下文压力，让每个 agent 产出更专注、准确。

```text
analyze-code/                      # 插件根
├── .claude-plugin/
│   └── plugin.json                # 清单 (name: code-analyzer)
├── skills/
│   └── analyze-codebase/
│       └── SKILL.md               # 编排入口: /code-analyzer:analyze-codebase
├── agents/
│   ├── project-scout.md           # 项目勘察员 (只读)
│   ├── feature-digger.md          # 功能深挖员 (只读 + 写报告, 可并行复用)
│   ├── integration-analyst.md     # 集成分析员 (只读)
│   └── report-writer.md           # 报告撰写员 (可写)
└── README.md
```

语言约定：插件内所有 `SKILL.md` 与 agent 定义文件的**正文与提示词均以中文为主**；frontmatter 的 `description` 也使用中文（便于阅读、且用于模型委托判断）。仅 `name` 等标识符使用小写英文连字符，遵循 Claude Code 规范。

## 3. 工作流（Skill 在主对话中编排）

Skill 作为「指挥」，把重活分派给 subagent，主线程只保留各 subagent 返回的精简摘要，避免上下文膨胀。

1. **勘察阶段** → 调用 `project-scout`（只读）：
   - 识别主开发语言、运行平台、总体架构。
   - 扫描 `docs/`（及 README、wiki、各模块内 README、代码注释/docstring 等文档源）的结构。
   - 梳理出**一级业务功能清单**，为每个一级功能同时映射出「相关代码路径」+「相关文档路径」。
   - 明确排除 CICD、镜像打包/发布等工程能力。
   - 返回：架构概览 + 一级功能清单（每项含简述、代码路径、文档路径）。

2. **深挖阶段** → 对每个一级功能（尽量并行）调用 `feature-digger`：
   - 接收该功能的「代码路径」与「文档路径」。
   - 强制双源流程：先读文档理解设计意图/原理/场景，再读代码验证；**交叉印证**，文档声明的能力以代码实现为准；发现文档与代码不一致时在报告中明确指出。
   - 产出：应用场景、解决的问题/痛点、优点、缺点、抽象工作原理（**非代码与函数间的调用原理**）、性能表现、该一级功能包含的二级功能清单及说明。
   - **直接写出 `./analysis-report/features/<功能名>.md`**，仅向主线程返回精简摘要。

3. **集成分析** → 调用 `integration-analyst`（只读）：
   - 结合文档中声明的集成点（配置、插件、适配器文档）与代码中的实际实现，分析实际部署环境中可与哪些其他项目/系统集成。
   - 返回集成分析摘要。

4. **汇总阶段** → 调用 `report-writer`（可写）：
   - 基于以上所有摘要写出 `./analysis-report/overview.md`（总体报告）。
   - 优先采用各 digger 已交叉印证过的结论，体现「文档描述」与「代码实现」的综合视角。

## 4. Agent 职责与配置

| Agent | name | 模型 | 工具 | 职责 |
|---|---|---|---|---|
| 项目勘察员 | `project-scout` | inherit | Read, Grep, Glob, Bash | 语言/平台/架构识别，扫描文档结构，产出一级功能清单并映射代码+文档路径 |
| 功能深挖员 | `feature-digger` | inherit | Read, Grep, Glob, Bash, Write | 深挖单个一级功能（文档+代码双源），直接写功能报告 |
| 集成分析员 | `integration-analyst` | inherit | Read, Grep, Glob, Bash | 分析外部集成能力（文档+代码双源） |
| 报告撰写员 | `report-writer` | inherit | Read, Write | 汇总产出总体报告 |

所有只读 agent 的 `Bash` 仅用于只读式探查（如 `ls`、列目录、统计），不做修改。

## 5. 统一排除规则（所有 agent 一律跳过）

- 测试目录：`test/`、`tests/`、`__tests__/`、`spec/`
- `.github/`（CI/工作流配置，属工程能力）
- 依赖/第三方目录：`vendor/`、`vendors/`、`node_modules/`、`third_party/`
- 延续 README 要求：排除 CICD、镜像打包/发布相关内容

该排除清单写入 Skill 与每个 agent 的指令，作为统一约束；同时作为 Skill 参数可覆盖/扩展的默认值。

## 6. 输出成果

在**被分析项目目录**下生成（报告正文为中文）：

```text
./analysis-report/
├── overview.md              # 总体报告
└── features/
    ├── <一级功能A>.md
    └── <一级功能B>.md
```

### 6.1 总体报告 `overview.md` 字段

- 项目主要基于什么语言开发、运行平台、总体职责
- 项目的应用场景
- 项目解决了什么问题或痛点
- 项目的优点
- 项目的缺点和限制
- 项目有哪些一级功能（含指向各功能详解报告的链接）
- 实际部署环境中可与哪些其他项目集成
- 综合视角说明：体现「文档描述」与「代码实现」的对照

### 6.2 一级功能报告 `features/<功能名>.md` 字段

- 功能的应用场景
- 解决了什么问题或痛点
- 优点
- 缺点
- 抽象工作原理（非代码与函数之间的调用原理；基于文档+代码综合得出）
- 性能表现
- 该一级功能包含哪些二级功能，各二级功能的说明
- 依据来源标注（文档 / 代码 / 二者一致 / 存在差异）

## 7. 关键约束与原则

- **双源综合**：每一层（总体/一级/二级）分析都必须同时结合文档与代码，禁止单方面分析。
- **聚焦业务功能**：只分析面向用户的业务能力，排除工程/运维能力。
- **上下文隔离**：高耗上下文的探查与深挖放在 subagent 内完成，主线程只收摘要。
- **可并行**：一级功能的深挖彼此独立，可并行委托多个 `feature-digger`。
- **中文优先**：插件内 Skill/agent 文本与输出报告均以中文为主。

## 8. 不做的事（YAGNI）

- 不分析测试代码、CICD、打包发布。
- 不做调用图/函数级调用链分析（工作原理为抽象层面）。
- 不引入 MCP server、hooks、LSP、monitors（本插件仅需 skill + agents）。
- 不使用实验性 Agent Teams 特性，采用稳定的主对话编排。
